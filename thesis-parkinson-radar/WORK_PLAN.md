## 2. Week 1 (Jul 30 – Aug 5) — data first, then code, then a real number

> **Ordering principle (revised 2026-07-29).** The data layer is settled *before*
> any model code is touched. Rationale: the EDA is largely complete (30 figures,
> 4 modules executed) but it is **not reproducible** (9 columns of
> `trial_features.csv` cannot be regenerated by today's `features.py`) and it is
> **out of date** (the batch and window-count confounds were found afterwards and
> appear in no figure). Fixing `train.py` first would mean building models on top
> of an unverified data layer. Days 1–2 close that gap; the code fixes move to
> Day 3, still ahead of the first training run.

### Day 1 · Data integrity: make the EDA reproducible
- 🔴 **Repair `features.py`.** Restore the 9 missing feature columns behind an
  explicit flag so the cached table can be regenerated from source.
- **Regenerate `trial_features.csv` from the `.mat` files** (~1 min of reads).
- **Re-run the full analysis chain** and diff against the published numbers:
  `src.eda`, `src.baseline`, `src.confound_analysis`, `src.diagnostics`.
- **Record any number that moves.** If the AUC grid, the duration confound or the
  permutation p-value shift, they shift *now* and `RESULTS.md` is corrected
  today, not in Week 6.
- **Write:** Methods §3.1 *Dataset*.

### Day 2 · Complete the data story, then decide the model input
- **Integrate the two late findings as first-class controls**, so the EDA reflects
  what we actually know:
  - acquisition **batch** (from `outputs/metrics/acquisition_batch.csv`): a
    batch × group figure, the `batch_only` = 0.664 null floor, and within-batch
    baselines;
  - **window count** per subject (27.3 control vs 30.9 PD) and its 0.621 floor.
- **Decide how the data reaches the models**, each choice justified from the data
  rather than by default:
  - window length / stride, argued from the trial-duration distribution
    (median 8.7 s, so 3.0 s/1.5 s yields only ~30 windows per subject);
  - normalisation, stating the amplitude/**bradykinesia** trade-off explicitly;
  - the per-subject **window cap** that neutralises the window-count confound.
- **Write:** Methods §3.2 *Preprocessing*, plus Results §4.1 *Dataset
  characterisation* and §4.2 *Identified confounds*. That material already
  exists, so it can be drafted now rather than in Week 2.

### Day 3 · The four code blockers, then build the cache

| # | Blocker | Fix |
|---|---|---|
| 1 | **Early stopping is degenerate** — in LOSO the val set is one subject → all labels identical → AUC hard-coded `0.5` every epoch. Reproduced: 20 epochs requested, **6 run, epoch-0 weights restored**. The model trains for *one epoch* and the run still finishes looking successful. | Inner-validation split, **or** fixed epoch budget. Add an assertion so it can't recur silently. |
| 2 | **Model selection on the test subject** — leakage; exactly what your Related Work criticises. | Same inner-val split. Then state it in Methods — it's a selling point. |
| 3 | **No `torch.save` anywhere** → Grad-CAM can never run | add `checkpoint_dir` + save per fold |
| 4 | **No grouped-CV splitter** | `grouped_cv()` with `StratifiedGroupKFold` |

```
58 subjects
├──  1 → TEST      (scored once; informs nothing)
├── ~8 → INNER VAL (stratified → both classes → early stopping works)
└── ~49→ TRAIN
```
Plus: `num_workers=4, persistent_workers=True`; seed every fold.

Then **run preprocessing** (**1.4 min**) using the configuration decided on Day 2,
producing the windowed `.npy` cache and its manifest.

**Write:** Methods §3.3 *Models*.

### Day 4 · First real LOSO
- SmallCNN smoke test on **grouped CV** — confirm the loss decreases and the
  pipeline is sane before spending a full LOSO.
- **Pre-register the configuration in a commit**, then run the full 58-fold
  SmallCNN LOSO (**~18 min**).
- Cheap ablation: **`ce` vs `stft_abs`** (one config change).
- Report against both null floors: `duration_only` 0.610 and `batch_only` 0.664.
- **Write:** Methods §3.4 *Validation* — state that model selection uses an inner
  split of training subjects only, and that the held-out subject is scored once.

### Day 5 · Consolidate + send
- Re-run anything shaky; assemble the Week-1 results snapshot.
- **Send the Methods chapter to the tutor.** First of four small asks.

## 9. 🔒 Pre-registration
Every design choice is tuned on the same 58 subjects then reported via LOSO. With
n=58 that optimism is real and can't be engineered away with a fixed cohort. So:
**commit the final config before the reporting LOSO**, report **one** number per
model family, state how many configurations were explored, and add a Limitations
sentence. Costs nothing; converts your weakest point into a demonstration of rigour.

### C. What counts as a good result
**Success is not a number. Success is a number you can defend.**

| Outcome | Verdict |
|---|---|
| **>0.70 within-batch AUC**, surviving the battery | **Strong** |
| **0.60–0.70 within-batch**, surviving the battery | **Solid** — real signal, honestly measured |
| **Chance within batch**, rigorous and complete analysis | **Still good** — first demonstration that radar-PD performance can be an acquisition artifact. Publishable. |
| High **pooled** number that collapses within batch | **Report the collapse.** That IS the finding. |
